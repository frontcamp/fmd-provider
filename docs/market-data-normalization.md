Предпосылки нормализации
------------------------

Данные поступают из множества источников, использующих разные форматы и сжатие (CSV, JSON, custom, zip, gz), чтобы постоянно не переписывать основной программный модуль под новые или изменившиеся старые данные, требуется нормализация хранилища рыночных данных.


Получение рыночных данных
-------------------------

Выбранные источники и ссылки для скачивания данных: `data/sources/download.txt`.
График обновления приведенных источников: `data/sources/availability.txt`.

Новые данные регулярно скачиваются из указанных источников в соответствующие каталоги. Каждый файл содержит дневной набор пост-трейдинговых данных. Дата набора определяется по данным источника.[^1] Часовой пояс зависит от биржи.

[^1]: Дата набора определяется по имени файла. Если дата в имени отсутствует, используются даты, указанные в трансакционных записях внутри файла. Если записи относятся к разным датам, датой набора считается дата, к которой относится большинство записей.

На момент составления этого документа (25.10.2026) структура каталогов с источниками выглядит так:

```text
/data
    /sources
        /BÖAG Börsen AG
            /DUSA - Börse Düsseldorf (Regulierter Markt)
            /DUSB - Börse Düsseldorf (Freiverkehr)
            /DUSC - Börse Düsseldorf Quotrix (Regulierter Markt)
            /DUSD - Börse Düsseldorf Quotrix (Freiverkehr)
            /HAMA - Börse Hamburg (Regulierter Markt)
            /HAMB - Börse Hamburg (Freiverkehr)
            /HAMP - Börse Hamburg Electronic Trading (Regulierter Markt)
            /HAMQ - Börse Hamburg Electronic Trading (Freiverkehr)
            /HANA - Börse Hannover (Regulierter Markt)
            /HANB - Börse Hannover (Freiverkehr)
        /Deutsche Börse Group
            /DETR - Xetra
            /DEUR - Eurex
            /DFRA - Börse Frankfurt
            /DGAT - Tradegate BSX
        /HAMN - Börse Hamburg LS-X (Freiverkehr)
            /RTS1 - Equity
            /RTS2 - Non-Equity
        /XEQT - Equiduct
```


Как это обрабатывается
----------------------

В каталоге `data/sources/` находится пакетный файл `normalize.cmd`, который рекурсивно запускает скрипты `normalize.py` во вложенных каталогах. Там же находятся каталоги в форматах:

### Основной формат

Формат: `data/sources/[биржа/]<MIC - Название места исполнения>/`

Примеры:

- `data/sources/BÖAG Börsen AG/DUSA - Börse Düsseldorf (Regulierter Markt)/`
- `data/sources/XEQT - Equiduct/`

### Вспомогательный формат для контейнеров данных

Формат: `data/sources/<биржа>/<ID - Название набора данных или контейнера>/`

Пример: `data/sources/Deutsche Börse Group/DETR - Xetra/`

### Вспомогательный формат для раздельных наборов данных

Формат: `data/sources/<MIC - Название места исполнения>/<ID - Название набора данных>/`

Примеры:

- `data/sources/HAMN - Börse Hamburg LS-X (Freiverkehr)/RTS1 - Equity/`
- `data/sources/HAMN - Börse Hamburg LS-X (Freiverkehr)/RTS2 - Non-Equity/`

### Обработка файлов

Задача `normalize.py` скрипта - обработать все файлы с рыночными данными в каталоге расположения скрипта.

Для каждого файла данных скрипт `normalize.py` должен:

+ считать файл в память
+ оставить только валидные[^2] трансакции с учётом обновлений[^3]
+ отсортировать трансакции по времени, для записей с одинаковым временем сохранить порядок источника
+ сохранить результат в симметричную папку `data/normalized/<data_path>/YYYYMMDD.zip`[^4]
+ удалить исходный файл с данными

[^2]: под валидными понимаются трансакции за указанную дату с набором данных, необходимым и достаточным для генерации OHLCV-свечей, включая условные "нулевые трансакции" с нулевым количеством, фиксирующие обновление цены.

[^3]: под обновлениями понимаются отмены и исправления.

[^4]: <data_path> - относительный путь от `data/sources/` к каталогу с исходными данными.

Результирующий архив должен содержать:

1) файл нормализованных данных: transactions.csv
2) файл с индексом финансовых инструментов: instruments.csv

Если в процессе обработки возникнут предупреждения или ошибки, лог-файл записывается рядом с архивом с таким же именем: `data/normalized/<data_path>/YYYYMMDD.log`.
В лог-файл следует записывать только аномалии нормализации, например: записи, чей тип не распознан; записи с недопустимыми данными и т.п.

Цель обработки - оставить только валидные записи, необходимые для формирования OHLCV-свечей и определения текущей цены на инструменты.
На этом процесс нормализации завершается.

Наборы данных группируются по торговым дням. Для одного торгового дня - один файл с данными. Исключений нет.

Наличие архива с нормализованными данными за некоторую дату является свидетельством произведенной нормализации, дополнительной фиксации в документации или реестре не требуется. В этом случае нормализатор должен просто удалить файл с исходными данными без повторной нормализации.

После нормализации исходные данные биржи удаляются. При необходимости архив исходных данных следует вести отдельно.


Формат данных
-------------

### Файл: transactions.csv

Формат: CSV со списком полей в первой строке
Кодировка: UTF-8, разделитель столбцов: `;`
Время исходных данных приводится к UTC
Формат даты/времени: RFC 3339, с дробной частью до 9 знаков: 2026-09-24T06:00:01.223081326Z
Десятичный разделитель: точка

Обязательные поля записи:

+ dataset    - идентификатор набора данных (например, DETR, RTS1 или RTS2), либо MIC места исполнения, если контейнер или другая классификация не определены.
+ mic        - MIC места исполнения сделки или установки цены
+ isin       - идентификатор инструмента
+ trade_time - время совершения сделки или установки цены
+ price      - цена
+ currency   - валюта цены (допускается обозначение EUR_PERC для процентов)
+ quantity   - количество; нулевое количество означает установку цены без сделки
+ quantity_unit - единица измерения количества (м.б. пустым)

Значение поля dataset:

1) если набор данных является контейнером (включает данные нескольких мест исполнения), то поле dataset содержит идентификатор этого контейнера;
2) если набор данных представляет данные одного места исполнения, то в поле dataset записывается его MIC.

ИСКЛЮЧЕНИЕ: набор данных HAMN разбит на RTS1 & RTS2 по категории инструментов в соответствии с нормативами отчетности MiFIR RTS1 и MiFIR RTS2, соответственно. Эти каталоги остаются как есть, без объединения файлов и переименований с указанием dataset=RTS1/2.

В поле mic сохраняется MIC места исполнения из исходной записи. Если он не указан, используется MIC, явно заданный в нормализаторе с учетом специфики источника данных.

Все остальные поля, кроме quantity_unit, должны быть определены, иначе запись не считается валидной и должна быть исключена.

Для определения названия инструментов следует создать отдельный модуль-реестр.

### Файл: instruments.csv

Формат: CSV со списком полей в первой строке
Кодировка: UTF-8, разделитель столбцов: `;`

Обязательное и единственное поле записи:

+ isin  - идентификатор инструмента (ключевое поле)


Особенности реализации
----------------------

Все нормализаторы должны наследовать один общий класс CustomNormalizer, код которого должен находиться в библиотеке проекта, в соответствующем файле: `libs/normalizer.py`.
В базовом классе должны быть определены абстрактные методы для определения даты по имени файла и для чтения записей исходного формата, т.к. эти параметры у всех бирж отличаются. А дальше они работают по сходной, описанной выше, логике.

Нормализатор настраивается под специфику каждого источника, прямо в каталоге с данными этого источника - это максимально просто и понятно. Через время можно будет зайти в каталог источника, открыть файл нормализатора и понять, что именно там настроено и как. Если же делать одну общую точку входа (общий скрипт, управляющий нормализацией), тогда придется создавать реестр соответствий имен файлов и форматов данных для каждого источника. Это отрывает реализацию от непосредственно самих данных, что со временем может стать проблемой (если конфигурация источников изменится) для поддержки и сопровождения проекта.

Исключаемые записи:

- записи, не входящие в указанную дату (такие остаточные данные с прошлой даты иногда попадаются)
- заявки
- котировки bid/ask
- служебные события
- записи без действительной цены
- сообщения об отмене и соответствующие им исходные сделки
- пустые строки без данных
- невалидные записи и записи, которые не удалось разобрать или классифицировать

Записи исправления сделок необходимо обработать - исправить соответствующие записи.

Финальный класс нормализатора должен определять метод чтения и парсинга исходной записи. Внутри этого метода следует распознать тип записи и вызвать соответствующий метод для обработки этой записи. То есть, метод парсинга отвечает за разбор, формирование унифицированного внутреннего представления данных, но обработку передает в родительский класс. Очевидно, родительский класс должен содержать методы для обработки записей всех возможных типов, в том числе, и неизвестных (для логирования).
