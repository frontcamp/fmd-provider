Назначение документа
--------------------

Документ задает регламент создания, оформления и проверки навыков ИИ-агента. Предназначен для пользователей и ИИ-агентов, выполняющих эти задачи.

Создание навыка
---------------

Критерии создания навыка:

1. Специализация. Инструкции относятся к определённому классу задач.
2. Переиспользование. Компетенция может потребоваться неоднократно.
3. Автономность. Навык имеет понятные границы и может развиваться независимо.
4. Ценность. Навык должен улучшать результат по сравнению с работой агента без него.

Первые три критерия определяют архитектуру, четвёртый - целесообразность.

Навык может описывать не только последовательность действий, но и содержать специализированные знания, стандарты, методы проверки или их комбинацию.

### Именование навыка

Именовать навык в соответствии со стандартом Agent Skills (kebab-case):

1. От 1 до 64 символов.
2. Строчные латинские буквы (a-z), цифры и дефисы.
3. Без пробелов, подчёркиваний и двойных дефисов.
4. Дефис не может стоять в начале или конце.
5. Значение поля `name` должно совпадать с именем каталога навыка.

Рекомендованный принцип именования: `<объект>-<действие>`.

Примеры: `code-review`, `document-translation`, `text-summarization`, `cat-detection`, `universe-debugging`.

Чего избегать:

- programming - слишком широкое;
- helper - непонятное назначение;
- code-tools - описывает инструменты, а не компетенцию;
- best-practices - не определяет область применения.

### Метаданные навыка

Файл `SKILL.md` должен начинаться с YAML-заголовка, содержащего обязательные поля:

- `name` - идентификатор навыка, соответствующий правилам именования.
- `description` - описание назначения навыка и условий его применения (не более 1024 символов).

После YAML-заголовка файл `SKILL.md` должен содержать инструкции в формате Markdown.

Требования к `description`:

1. Конкретно указывать, какие задачи решает навык.
2. Определять ситуации, в которых навык следует применять.
3. Содержать характерные ключевые слова для определения применимости навыка.
4. Избегать общих и неоднозначных формулировок.
5. При необходимости указывать ситуации, в которых навык применять не следует.

### Оформление правил

Каждое правило должно быть оформлено следующим образом:

```Markdown
### [~] ПРАВИЛО

...

ИСКЛЮЧЕНИЕ:

...

ПРИМЕЧАНИЕ:

...

<!--
@comment 2026-11-08 by Maksym
Какой-то редакционный комментарий к правилу.
@review 2026-11-09 passed, status up
@review 2026-11-10 passed, status down
-->
```

где `[ ]` - статус правила или этап внедрения:

- `[~]` - идея, набросок
- `[-]` - черновик, активная доработка (этап стабилизации)
- `[+]` - рабочая версия (кандидат на утверждение)
- `[$]` - утвержденное правило (возможен мелкий тюнинг)
- `[!]` - подтвержденное правило (без необходимости не трогать)

Первые три статуса `<~|-|+>` отвечают за редакционную готовность правила. Последние два статуса `<$|!>` отвечают за его практическое подтверждение:

- `$` - правило применялось без выявленных проблем минимум в одном проекте;
- `!` - правило применялось без выявленных проблем минимум в двух проектах.

Решение об изменении статуса правила принимает редактор. При существенном изменении содержания отдельного правила его практическое подтверждение пересматривается. Редактор определяет новый статус с учётом характера изменений.

Обозначение редакционного статуса и HTML-комментарий не являются частью правила.

Теги в прописном регистре (`ИСКЛЮЧЕНИЕ:`, `ПРИМЕЧАНИЕ:` и др.) и служебные теги в HTML-комментарии вида `@tagname` относятся только к правилу, под которым они находятся.

Тег `ПРАВИЛО` является обязательным, остальные используются по необходимости.

ВАЖНО: HTML-комментарий не должен содержать информацию, которую ИИ-агент может потенциально трактовать как инструкции к правилу. Этот блок предназначен исключительно для редакторских целей и фиксации истории изменения статусов. Следует периодически очищать или удалять эти комментарии, оставляя только существенные для будущих редакций или состояний.

Вышеописанный механизм позволяет структурировать и стандартизировать оформление правил, определяет их статус и регламентирует оформление технических метаданных.


Ресурсы навыка
--------------

Организация навыка в виде каталога предусматривает размещение вспомогательных файлов, которые навык может использовать по необходимости.

Рекомендуемая файловая структура навыка:

```
skills/
    <skill_name>/ - каталог навыка
        SKILL.md - основные инструкции навыка
        references/ - дополнительные знания, правила, справочники
        scripts/ - исполняемые программы
        assets/ - прочие ресурсы
```

Причина разделения - прогрессивная загрузка контекста (Progressive Disclosure).

Если среда ИИ-агента поддерживает прогрессивную загрузку, информация предоставляется поэтапно:

1. Описания доступных навыков.
2. Инструкции выбранного навыка.
3. Дополнительные материалы по необходимости.

В таком случае не требуется одновременной загрузки всех доступных инструкций, а только используемых.


Проверка навыка
---------------

Перечень критериев качества:

1. Валидность. Соответствие стандарту Agent Skills.
2. Применимость. Корректность определения условий использования.
3. Полнота. Покрытие необходимых сведений и действий для выполнения задач навыка.
4. Однозначность, проверяемость и непротиворечивость.
5. Специализация. Соблюдение границ компетенции.
6. Эффективность. Отсутствие избыточных инструкций, рациональность использования контекста и отсутствие неоправданно сложных процедур.
7. Автономность. Достаточность информации для выполнения задач.
8. Безопасность. Отсутствие нежелательных действий.

### Проверка потенциальных проблем

Если пользователь просит оценить или проверить качество навыка, ИИ-агент должен проанализировать исследуемый навык, учитывая его назначение, и дать экспертное заключение (опираясь на рекомендации признанных экспертов или крупных IT/AI-компаний) по каждому критерию из списка выше. Для каждого несоответствия указать конкретный фрагмент, потенциально возможную ошибку или потенциальное затруднение и ожидаемую пользу изменения. Если проблему нельзя обосновать - правку не предлагать.

### Практическое выявление проблем

Если пользователь просит оценить практическую применимость навыка, действовать в соответствии с общей практикой использования субагентами:

- Выделить критические или спорные требования и подготовить задачи с заранее определёнными критериями успеха, по критериям из списка выше, для которых практическое тестирование применимо.
- Передать исполнителю навык, необходимые материалы и обычное задание, без переписки с разбором предполагаемой ошибки.
- Получить фактический результат: ответ, созданные файлы, выполненные действия.
- Сопоставить результат с критериями и в виде списка перечислить нарушения.

### Предложения по улучшению

Если пользователь спрашивает, что можно улучшить в навыке, ИИ-агент должен найти в сети аналоги в авторитетных источниках (рекомендации признанных экспертов или крупных IT/AI-компаний), сравнить с проверяемым навыком и дать экспертные вариативные рекомендации по улучшению на основании этого сравнения.
